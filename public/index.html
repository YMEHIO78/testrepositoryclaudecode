System spec

Data model, integrations, and security notes for building and hosting this as a real web app on Railway.

Security — read this before deploying

Railway's proxy gives you HTTPS/TLS and network isolation automatically. It does not secure the app itself — that's on the app:

  • Login for you. This app should sit behind its own authentication (a login screen, or a Railway private network + something like Cloudflare Access in front of it) — not a public URL anyone can browse to.
  • OAuth, not passwords. Connect Outlook and Wave through their OAuth flows. The app never sees or stores your Microsoft or Wave password.
  • Encrypt tokens at rest. OAuth access/refresh tokens for Outlook and Wave get encrypted in the database (e.g. with a key stored in Railway's environment variables, not committed to the repo) — plain-text tokens in a table are the most common way this kind of app gets compromised.
  • Secrets in environment variables only. Client IDs, client secrets, and encryption keys live in Railway's variable store, never in source control.
  • Scope the OAuth permissions tightly. Request read/send mail and calendar scopes for the two Outlook inboxes — not full directory or admin scopes.
  • Session expiry + rate limiting on any login and API endpoints, so a leaked link or brute-force attempt can't just sit there.
1 · Companies

Leads and clients in one table

One row per organization, from cold name to retained client. Leads and clients stay in the same table — the stage field is what moves them, and splitting into two tables loses the history.

fields: name, logo_url, stage (enum: not_contacted, in_contact, engaging, offer_sent, client, rejected), health (enum: green/amber/red), industry, source, website, billing_address, site_address, timezone, owner_id, client_since, wave_customer_id
relations: contacts[], package_lines[], projects[], tickets[], files[], invoices[], emails[]
computed: contract_value = sum(package_lines.line_total) · open_tickets = count(tickets where status != done) · last_touch = max(emails.date) · days_since_touch = now - last_touch
2 · Contacts

Humans, not organizations

fields: full_name, role, email, phone, mobile, is_primary (bool), is_decision_maker (bool), notes, linkedin_url
relations: company_id, tickets_raised[], emails[]
3 · Package catalogue

Three rows, rarely edited

rows: Manual Data · Data Warehousing · Data Analysis
fields: unit_price, unit_of_sale, billing_type (enum: one_off, retainer, hourly), default_duration_days, scope_template
4 · Package lines

Where quantities live

One row per package sold to one company, carrying a quantity — this is what makes "Manual Data (7)" or "Warehousing (1)" work as a single, queryable number instead of free text.

fields: quantity, unit_price_override, status (enum: proposed, signed, delivered, cancelled), start_date
relations: company_id, package_id, project_id, invoice_id
computed: unit = unit_price_override ?? catalogue.unit_price · line_total = quantity * unit
5 · Projects
fields: name, stage (enum: scoping, build, review, handover, blocked, closed), start_date, due_date, budget, owner_id, priority
relations: company_id, package_line_id, tasks[], time_entries[], expenses[], files[], tickets[], invoices[]
computed: progress = tasks_done/tasks_total · logged_cost = sum(time_entries.cost) · margin = budget - logged_cost - expenses · health = at_risk if days_left < 5 and progress < 80
6 · Tasks
fields: title, status (enum: todo, doing, blocked, done), assignee_id, due_date, estimate_hours, is_milestone
relations: project_id, ticket_id (optional), time_entries[]
7 · Tickets

The service desk

fields: ticket_no (auto, TKT-###), subject, status (enum: new, in_progress, waiting_on_client, done), priority (enum: low/medium/high/urgent), type, opened_at, sla_due_at, assignee_id, source (enum: email, form, call), summary, source_email_id, resolution
relations: company_id, contact_id, project_id, tasks[], files[]
computed: sla_due_at = opened_at + (4h urgent / 24h high / 72h other) · breach_risk = due_soon if open and <24h left
8 · Emails

A log, not a mail client

fields: subject, from_email, to_inbox (enum: clientcare@, admin@), received_at, snippet, graph_message_id, handled (bool), needs_reply (bool)
relations: company_id, contact_id, ticket_id
9 · Files index
fields: file_name, storage_url (OneDrive), type (enum: source_data, working_file, deliverable, contract, template), size, sharing (enum: internal, client_link), modified_at, retention_until
relations: company_id, project_id, ticket_id

Keep large source data (raw exports, big scans) in OneDrive and store the link. Deliverables and contracts can be stored directly if you add object storage (e.g. S3-compatible) later — either way, the index table is what makes a file findable from the client record.

10 · Invoices & 11 · Expenses

Mirrors of Wave

invoices: number, amount, issued_date, due_date, status (enum: draft/sent/paid/overdue), wave_invoice_id, company_id, project_id
expenses: item, amount, date, category (enum: contractor, infrastructure, software, other), treatment (enum: rebilled, overhead), company_id, project_id, person_id

Rule: Wave stays the ledger. Amounts are entered once, in Wave, and synced in — never edited or reconciled directly in this app.

12 · People & time entries
people: name, role, type (enum: owner, employee, contractor), rate, status, access_level, start_date
time_entries: date, hours, notes, person_id, project_id, task_id · computed: cost = hours * rate

Contractors get access scoped to the projects and tickets they're assigned to only — never to Companies, Invoices, Expenses, or People.

Email → ticket flow

How a ticket gets created

1. A client email arrives on clientcare@ or admin@. 2. The Graph webhook logs it to Emails and links it to a Company by sender domain (unmatched senders land in a "needs linking" view). 3. Nothing else happens automatically — the email sits in the Inbox view with a Create ticket button. 4. Pressing it sends the email body to a one-shot model call that fills in subject, type, priority, a short summary, and a suggested first step, and copies attachments to the client's folder. 5. Low-confidence fields (usually priority and SLA) are flagged for review before the ticket goes live.

This is a single API call per ticket, not a standing assistant — it has no memory, no ongoing access to the workspace, and no ability to act on its own.

Build order
1. Package catalogue, People — small and static. 2. Companies, Contacts, Package lines. Add the computed fields. 3. Projects and Tasks; wire the rollups. 4. Tickets and Emails; add SLA logic. 5. Files, Invoices, Expenses, Time entries. 6. Build the Dashboard last, from the tables above. 7. Wire the two automations: Outlook → Emails webhook, and the Create ticket action. 8. Deploy to Railway; add auth, encrypted token storage, and OAuth scopes before connecting real accounts.
